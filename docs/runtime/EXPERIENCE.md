# 경험 정본 계약

경험 Markdown은 회사·JD와 무관한 사실 정본이다. JD 키워드, 특정 회사 적합도, 지원 문항용 문장은 경험 파일에 넣지 않는다. 그 해석은 `01_JD분석.md` · `02_직무적합성.md` · `03_소재매핑.md`에서만 한다.

## 두 형식이 함께 있다

| 형식 | 표시 | 요구 구조 |
|---|---|---|
| 기존 형식 | 없음 | `사실 · 근거 · 상태`만. 추가 검사 없음 |
| experience-v2 | 머리 정보의 `- 경험 형식: experience-v2` | 아래 유형별 구조 검사 적용 |

experience-v2는 opt-in이다. 기존 경험을 일괄 변환하지 않는다. 새로 만드는 경험과 실제로 다시 사용하면서 근거를 보강하는 경험만 표시를 붙인다. 표시를 붙이는 순간 그 파일에만 검사가 적용되고, 다른 경험은 영향을 받지 않는다.

claim-id와 `검증됨 · 확인 필요 · 사용 금지` 상태는 형식 전환으로 바뀌지 않는다. 형식을 올린다는 이유로 상태를 승격하지 않는다.

## 머리 정보

```markdown
- 경험 형식: experience-v2
- 경험 유형: 업무 | 연구 | 프로젝트 | 수업 | 자격 | 활동
- 기간:
- 소속·형태:
- 본인 역할:
- 현재 상태:
```

## 유형별 필요한 절

`업무 · 연구 · 프로젝트`는 서사형이다. 다음을 모두 쓴다.

- `## 문제와 목표`
- `## 본인의 판단과 행동`
- `## 데이터·도구·방법`
- `## 산출물·결과·한계`
- `## 사용하면 안 되는 표현` (또는 `## 사용 시 주의`)
- `## 원자료`

`자격 · 수업 · 활동`은 `## 검증된 사실`과 `## 원자료`만 있으면 된다. 어학 성적이나 수강 과목에 문제–행동–결과 서사를 만들어 붙이지 않는다.

`데이터·도구·방법`과 `산출물·결과·한계`는 서사형에서 권장하지만 구조 검사 대상은 아니다. 쓸 내용이 없으면 비워 두고, 없는 판단·도구를 지어내지 않는다.

## claim 필드

```markdown
### <CLAIM-ID>
- 사실: 지원서에 쓸 수 있는 한 문장
- 근거: 원본 파일·로그·커밋 위치
- 상태: 검증됨 | 확인 필요 | 사용 금지
- 유형: 문제 | 판단 | 행동 | 산출물 | 결과 | 협업 | 역량 | 한계
- 본인 기여: 팀 결과와 구분되는 본인 몫
- 방법·도구: 이 사실과 직접 관련된 데이터·도구·방법
- 결과·상태: 확인된 결과와 검증 범위
```

`사실 · 근거 · 상태`는 모든 형식에서 필수다. `유형`은 experience-v2에서 필수다. `본인 기여 · 방법·도구 · 결과·상태`는 해당할 때만 쓰며, `유형: 결과`인 claim에는 `결과·상태`가 필요하다. 이미 `사실`에 있는 내용을 다른 필드에 다시 적지 않는다.

기존 형식 경험에서도 이 필드들을 쓸 수 있다. 값이 없는 필드는 저장되지 않으므로 기존 문항의 입력 해시가 바뀌지 않는다.

## 검색과 읽는 순서

경험이 많아지면 전체를 모델에 넘기지 않고 아래 순서로 좁힌다. 전체 경험 × 전체 JD 요구의 조합을 한 번에 전달하지 않는다.

```powershell
node scripts/apply-packet.mjs catalog --mode index --out .work/apply/current/index.md
node scripts/apply-packet.mjs catalog --mode claims --files profile/experiences/<경험>.md --out .work/apply/current/claims.md
```

1. `--mode index`: 경험 파일별 제목·경험 유형·본인 역할·검증 claim 수. 어느 경험을 열지 정한다.
2. `--mode claims`: 해당 경험의 claim 요약. `유형`과 `방법·도구`가 함께 표시된다.
3. 필요한 근거만 `정본: <파일>:<줄>` 위치에서 직접 확인한다.

`--query`는 claim의 `사실 · 유형 · 본인 기여 · 방법·도구 · 결과·상태`와 경험의 제목·머리 정보·서사 절까지 함께 찾는다. 사실 문장에 도구 이름이 없어도 `데이터·도구·방법` 절에 있으면 그 경험의 claim이 검색된다. `--files` · `--limit` · `--offset`으로 범위를 나누며, 출력의 표시 범위·미검토 범위 경고를 그대로 읽는다. **검색 결과 없음은 경험이 없다는 증명이 아니다.**

## 구조 검사와 사람의 검토

`node scripts/validate-profile.mjs`는 experience-v2 경험에 대해 다음만 판정한다.

- 경험 유형 누락·오값, 현재 상태 누락, 원자료 절 누락
- 서사형의 본인 역할·서사 절·표현 제한 절 누락
- claim 유형 누락·오값, 중복 claim-id
- verified claim의 사실·근거 누락
- `유형: 결과`인데 `결과·상태`가 빈 경우
- 현재 상태가 미확인인데 결과 claim이 `검증됨`인 구조적 모순

코드는 다음을 판정하지 않으며 판정했다고 보고해서도 안 된다.

- 경험 설명이 의미상 완전한지
- 본인 기여가 실제로 충분한지
- 결과와 행동의 인과관계가 맞는지
- 특정 JD에 적합한지
- 검색되지 않은 경험이 실제로 없는지

이 판단은 사용자와 모델이 원문을 보고 한다. 구조 검사 통과를 의미 검증 통과로 바꿔 부르지 않는다.

## JD 매칭과의 연결

`02_직무적합성.md`가 claim을 인용하면 그 claim의 내용과 경험 파일의 공통 문맥이 요구 해시에 들어간다.

- `사실 · 근거 · 상태 · 유형 · 본인 기여 · 방법·도구 · 결과·상태` 변경 → **그 claim에 연결된 요구만** 재검토 대상
- `본인 역할 · 현재 상태 · 표현 제한 절` 변경 → 그 **파일의 claim에 연결된 요구 전체** 재검토 대상
- 연결되지 않은 경험·claim 변경 → 기존 매칭과 지원서 문항을 무효화하지 않음

변경 확인과 기록은 [JD 매칭 계약](JD_MATCHING.md)의 `jd-map.mjs check` · `record`를 따른다.
