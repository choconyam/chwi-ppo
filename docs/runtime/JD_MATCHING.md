# JD 문장별 분석·경험 연결

사람이 읽고 수정하는 정본은 Markdown이다. `00_JD.md`는 보존하고, 공식 확인된 소수 후보를 상세 분석할 때 `01_JD분석.md`와 `02_직무적합성.md`에 아래 형식을 쓴다. 목록 탐색의 모든 후보에 긴 분석을 만들지는 않는다. 자격이 명백히 불충족이면 기존 한 줄 종료 규칙을 유지한다.

## 무엇을 어디에 남기는가

| 파일 | 책임 |
|---|---|
| `00_JD.md` | 공식 원문·URL·확인 시각·사용자 메모, 후속 단계가 덮어쓰지 않음 |
| `01_JD분석.md` | 원문 요구별 고정 ID·출처·실무 해석, 지원자 경험을 보지 않고 작성 |
| `02_직무적합성.md` | 모든 요구 ID에 연결 판정·검증 claim·이유·한계·탐색 범위 |
| `03_소재매핑.md` | 문항 → 요구 ID → claim, 주력/보조 소재와 과장 금지선 |
| `.work/.../matching.json` | 정본에서 만든 변경 비교용 검토 기록, 사람이 읽을 정본이나 PASS 아님 |

첫 분석에서 메인이 원문의 수행업무·필수·우대·지원 조건을 한 번 끝까지 대조해 빠진 요구가 없는지 확인한다. 한 문장에 독립 요구가 여러 개면 나누고, 동일 요구의 반복은 출처를 모두 남겨 하나로 묶을 수 있다. 일반 소개·광고 문구 등 제외한 범위와 이유도 01의 공통 문맥에 적는다. 기존 ID는 순서를 바꿔도 유지하며 삭제한 ID를 다른 요구에 재사용하지 않는다.

원문 인용과 `[공식자료 확인]`, `[외부자료 확인]`, `[합리적 추정]`을 구분한다. 회사 사업·제품·공정과의 관계, 왜 필요한 일인지, 데이터·도구·협업 상대·산출물을 해당 요구 해석에 연결한다. 확인한 자료의 URL·확인일을 적고 근거 없는 회사 내부 사정은 단정하지 않는다. 추정 업무를 실제 수행 경험으로 바꾸지 않는다. 업무 비중 숫자·가상 하루 일정·면접 질문 전체 세트는 자동 생성하지 않는다. 추가 기업 분석도 선택 직무 이해에 필요한 범위만 한다.

## Markdown 형식

01의 공통 요약은 요구 블록 앞에 짧게 쓴다. 아래는 **가상 형식 예시**다. 실제 공고의 원문으로 대체한다.

```markdown
# 직무 분석
- 매칭 형식: jd-map-v1
- 원문 대조: 수행업무·필수·우대·조건 전체 확인 / 제외: 일반 홍보 문구
- 직무 요약: 데이터를 분석해 운영 판단에 필요한 근거를 만드는 직무

### JD-001
- 구분: 업무
- 원문: 운영 데이터 분석
- 출처: 00_JD.md 수행업무 첫째 항목
- 업무 해석: [합리적 추정] 운영상의 문제를 지표로 정의하고 원인 후보를 비교한다.
- 산출물: [합리적 추정] 지표 정의와 분석 보고서
- 필요 역량: 데이터 정제, 비교 기준 설정, 결과 해석
```

02는 전체 자격 `eligible/ineligible/needs-review`, 적합성 `진행/주의/재검토` 및 공통 주의사항을 블록 앞에 둔다. 이후 01의 **모든 ID**를 같은 제목으로 작성한다.

```markdown
# 직무 적합성
- 자격: needs-review (필수 조건은 공식 근거와 별도 확인)
- 적합성: 주의

### JD-001
- 판정: 전이
- claim: WORK-001
- 연결 이유: 다른 분야에서 운영 데이터를 정제·비교한 방법을 옮겨 쓸 수 있다.
- 한계: 해당 산업의 현장 문제를 해결한 경험은 확인되지 않았다.
- 탐색 범위: 경험 인덱스 전체와 work.md 확인 / 나머지 원자료 미검토
```

- 제목은 정확히 `### JD-001` 형식이다. 각 필드는 한 줄로 쓰며 정본에 예시 코드 블록을 남기지 않는다.
- 구분: `업무 / 필수 / 우대 / 조건`. 01의 원문은 00에 실제 존재하는 연속 문자열이어야 한다. 출처에는 섹션·항목/행 등 다시 찾을 수 있는 위치를 쓴다.
- 판정: `직접 / 전이 / 부분 / 미확인 / 해당없음`. 직접은 같은 업무를 수행한 근거, 전이는 다른 맥락의 방법을 옮길 수 있는 근거, 부분은 요구의 일부만 입증하는 경우다. 단순한 도구명 일치는 직접 연결의 근거가 아니다.
- 연결한 claim은 쉼표로 나열하며 `검증됨`만 허용한다. `미확인/해당없음`은 `claim: 없음`으로 쓰고 이유를 남긴다. 해당없음으로 필수 조건을 우회하지 않는다.
- 미확인은 아직 근거를 못 찾았다는 뜻이지, 경험이 없거나 지원 불가하다는 판정이 아니다. 검색어·확인 파일·미검토 범위와 다음 확인사항을 남긴다.
- 요구 ID를 모두 처리했다고 자격 충족이나 적합성 PASS가 되는 것은 아니다. 필수 요건은 전체 자격 판단에서 따로 확인한다.

## 경험이 많을 때의 입력 절약

전체 원자료를 다시 읽거나 모든 요구 × 모든 경험 조합을 모델에 보내지 않는다. 최초 intake의 검증된 경험 정본과 요약을 재사용한다.

```powershell
node scripts/apply-packet.mjs catalog --mode index --limit 30 --offset 0 --out .work/matching/index.md
node scripts/apply-packet.mjs catalog --files profile/experiences/work.md --out .work/matching/selected.md
node scripts/apply-packet.mjs catalog --query 분석 --limit 30 --out .work/matching/search.md
```

1. 경험 제목·파일·검증 claim 수의 인덱스를 먼저 읽고 관련 또는 모호한 경험을 고른다. 페이지가 남으면 다음 offset으로 이어간다.
2. 선택 파일의 claim 요약과 관련 역할·상태·표현 제한을 읽고 매칭한다. 키워드 검색은 보조 수단이며 동의어·다른 분야의 전이 경험을 놓칠 수 있다.
3. 출처가 모호하거나 충돌할 때만 연결된 원자료 위치를 연다. 인덱스·검색 결과 밖을 확인했다고 쓰지 않는다.

catalog는 정본을 로컬 코드로 읽어 출력만 줄인다. 스크립트 자체는 모델을 호출하지 않지만 출력 내용을 모델이 읽는 토큰은 든다. 최초 정리·해석 비용은 남고, 실제 절감률은 측정 없이 제시하지 않는다. `--files`는 쉼표 구분 상대 경로, `--query`는 ID·사실·경로에 대한 단순 부분 검색이다. 큰 출력은 `--limit`과 `--offset`으로 나눈다.

## 전체 구조 검사와 변경분만 검토

```powershell
node scripts/jd-map.mjs check --jd companies/회사/직무/00_JD.md --analysis companies/회사/직무/01_JD분석.md --fit companies/회사/직무/02_직무적합성.md --state .work/matching/회사-직무.json
```

검사는 전체 요구 목록과 연결표의 누락·중복·추가 ID, 원문 인용 존재, 필수 필드, claim 존재·검증 상태를 로컬 코드로 확인한다. 구조 오류는 종료 코드 1로 알린다. 구조가 유효하면 아래 변경 요약을 반환하며 파일을 수정하지 않는다.

| 출력 | 필요한 판단 |
|---|---|
| `sourceReviewRequired` | 공식 원문이 바뀜. 추가/삭제/변경 구간의 요구 분해와 누락을 대조 |
| `contextReviewRequired` | 01/02 공통 판단·주의사항이 바뀜. 관련 해석 재확인 |
| `changed` | 해당 요구·연결 판단 또는 연결 claim·공유 역할 제한이 바뀜. 그 ID만 재판단 |
| `removed` | 이전 요구 ID가 사라짐. 의도한 삭제인지 원문과 대조 |
| `candidateClaims` | 새로 추가되거나 바뀐 claim. 관련 요구, 특히 미확인 항목의 후보만 다시 탐색 |
| `reusable` | 연결 입력이 같음. 원문·공통 문맥까지 같으면 기존 판단 재사용 |

같은 경험 파일에서 무관한 claim만 바뀌면 기존 연결을 무효화하지 않는다. 본인 역할·금지 표현·서술 절 등 claim 블록 밖의 변경은 그 경험의 연결 항목 전체에 영향을 준다. 예외로 `## 원자료` 절은 파일 경로 목록이므로 바뀌어도 기존 연결과 문항을 재검토시키지 않는다. 새 claim은 기존 매칭의 오류를 뜻하지 않으므로 기존 문항을 자동 무효화하지 않는다. 삭제된 비배정 claim은 기존 연결에 영향이 없고, 배정 claim 삭제·검증 취소는 구조 오류로 차단한다.

메인이 원문 분해와 필요한 변경 항목을 실제로 검토한 뒤 기록한다. 최초 실행에서는 전체 요구와 연결을 검토해야 한다. 변경이 없으면 record를 반복하지 않는다.

```powershell
node scripts/jd-map.mjs record --reviewed yes --jd companies/회사/직무/00_JD.md --analysis companies/회사/직무/01_JD분석.md --fit companies/회사/직무/02_직무적합성.md --state .work/matching/회사-직무.json
```

이 기록은 별도 사실 검수나 final PASS가 아니다. 스크립트는 원문의 요구를 빠짐없이 추출했는지, 연결 이유가 타당한지, 수행 결과가 사실인지 증명할 수 없다. 구조 검사 통과를 의미 검토로 대체하지 않는다. 기록은 `.work/` 내부 JSON에만 저장하며 필요하면 Markdown 정본에서 다시 생성한다.

## apply 연결·기존 자료 호환

새 상세 분석에는 위 형식을 사용한다. 기존 분석·지원서를 일괄 변환하지 않는다. 표시가 없는 기존 01은 종전 전체 문서 해시 방식으로 계속 동작한다. 새로운 요구 분해가 필요한 때에만 형식을 전환하며 과거 PASS를 새 해시로 옮기지 않는다.

03은 문항마다 `요구 ID / claim / 선택 이유 / 한계`를 기록한다. 모든 JD 요구를 자소서에 억지로 넣지는 않는다. `application-request.json`에 다음 필드를 추가한다.

```json
{
  "matchingState": ".work/matching/회사-직무.json",
  "questions": [{
    "id": "Q1", "prompt": "공식 문항", "source": "공식 위치", "limit": 1000,
    "requirementIds": ["JD-001"], "claimIds": ["WORK-001"]
  }]
}
```

위는 추가 필드 예시이며 나머지 필수 필드는 [apply 계약](APPLY.md)을 따른다. 각 요구에 연결된 claim 중 최소 하나를 해당 문항에 배정한다. 비직무·가치관 문항은 `requirementIds: []`와 비워 둔 이유인 `requirementNote`를 명시할 수 있다. 요구 근거 외에 문항에 필요한 검증 claim을 추가 배정할 수 있다.

prepare는 검토 기록이 현재 Markdown·연결 claim과 같은지 확인한다. 변경됐다면 check 결과의 해당 항목을 검토·기록한 뒤 prepare한다. 새 형식의 packet.md는 공통 분석·주의사항과 문항에 선택된 요구·매칭·claim만 한 번씩 담는다. 검증용 JSON 전문을 모델에 관례적으로 넘기지 않는다.

무관한 요구 연결만 바뀌면 관련 없는 문항의 해시·유효한 체크포인트는 유지된다. 선택 요구·선택 claim·공유 문맥·공식 원문·문항·자격 판단이 바뀌면 해당 입력의 기존 검수는 재사용하지 않는다. 공식 원문/공통 판단 변경은 보수적으로 전체 문항에 영향을 준다. 실제 원문 변경 여부의 온라인 재확인은 discover/final의 기존 규칙을 따른다.
