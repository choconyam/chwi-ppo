# 다른 사용자를 위한 시작 안내

## 준비물

- Codex 또는 Claude Code 중 하나
- 현재 채용 공고를 찾기 위한 인터넷 연결
- 이력서·성적표·프로젝트 README 등 본인 자료

캘린더만 볼 때는 Node.js가 필요하지 않다. 전체 파이프라인의 자동검증 스크립트를 실행하려면 Node.js 20.19 이상이 필요하다. 사용 중인 Codex·Claude 환경에서 `node --version`이 동작하면 별도로 설치하지 않아도 된다.

## 1. 저장소 받기

별도 npm 설치 명령은 필요하지 않다. [GitHub 저장소](https://github.com/choconyam/chwi-ppo)에서 `Code → Download ZIP`을 선택해 압축을 푼다. Git을 사용한다면 다음처럼 복제한다.

```powershell
git clone https://github.com/choconyam/chwi-ppo.git
cd chwi-ppo
```

프로젝트 폴더 자체를 Codex 또는 Claude Code에서 연다. 하위 폴더가 아니라 `AGENTS.md`가 있는 최상위 폴더에서 시작해야 저장소 로컬 스킬을 찾을 수 있다.

저장소를 받는 데 npm은 쓰지 않지만, 전체 파이프라인의 변경 감지·형식 검사 스크립트에는 Node.js 20.19 이상이 필요하다. 상황판만 보는 경우는 예외다. React 상황판 자체를 개발할 때의 npm 의존성은 별도이며 `run-dashboard-dev.cmd`가 필요할 때 설치한다.

## 2. 본인 자료 정리

원본 파일은 저장소 밖의 개인 폴더에 두어도 된다. 경로를 지정해 intake를 실행한다.

| 환경 | 실행 예시 |
|---|---|
| Codex | `/intake C:\내자료` |
| Claude Code | `/intake C:\내자료` |

에이전트가 `profile/PROFILE.md`와 경험별 Markdown을 만든다. `[확인 필요]` 질문에는 사용자가 직접 답해야 하며, 답하지 않은 사실은 지원서에 사용할 수 없다.

이미 정리한 자료는 다시 추출하지 않고, 추가·변경된 파일과 관련 경험만 갱신한다. 실행이 중단됐다면 같은 원자료 경로로 `/intake`를 다시 요청한다. 완료된 소단위 결과는 재사용하고 미완료 부분부터 이어간다. 프로젝트 README와 요약 보고서를 우선 읽으므로 모든 코드와 로그를 먼저 정리할 필요는 없다. 경력자는 경력기술서와 담당 업무·근무 기간을 함께 제공한다. 불확실한 항목 하나 때문에 다른 확인된 경험까지 사용이 막히지는 않는다.

## 3. 지원할 공고 찾기

| 환경 | 실행 예시 |
|---|---|
| Codex | `/discover 반도체·전자·AI 신입, 수도권·충청권` |
| Claude Code | `/discover 반도체·전자·AI 신입, 수도권·충청권` |

“자소설닷컴 이번 달 공고에서 내 경험에 맞는 대기업을 찾아줘”처럼 요청해도 된다. 경력직은 신입 예시 대신 “내 경력으로 지원할 수 있는 직무”라고 요청하면 된다.

채용 캘린더·목록에서 사용자 조건에 맞는 기업과 세부 직무를 추린 뒤, 후보의 공식 페이지에서 지원 자격과 마감을 확인한다. 회사에 여러 직무가 있으면 각각 비교하고, 필수 관련 경력과 우대 조건을 구분한다. 정리된 개인 경험을 바탕으로 추천 이유와 부족 요건을 알려준다. 기업명만 보고 제외하거나 공식 근거가 없는 정보를 확정하지 않는다.

목록 일부만 읽었으면 확인한 범위와 남은 후보를 보여준다. “이어서 찾아줘”라고 하면 저장된 목록에서 계속한다. 검색 후 바로 지원서를 작성할 수 있으며 캘린더 등록은 선택이다.

## 4. 회사별 지원서 작성

| 환경 | 실행 예시 |
|---|---|
| Codex | `/apply 회사명 직무명` |
| Claude Code | `/apply 회사명 직무명` |

선택한 JD의 문항별로 검증된 경험을 배정하고, 글자수에 맞춰 초안을 작성한다. 이후 원자료와 대조해 사실·수치·역할·완료 상태를 검수하고 지적된 부분만 수정한다. 실제 제출 직전 독립 최종 검수까지 요청하려면 끝에 `final`을 붙인다. 에이전트는 지원 사이트에 자동 제출하지 않는다.

수정할 때는 해당 문항과 변경된 근거만 다시 처리한다. 로그인 뒤의 문항을 읽을 수 없으면 질문 원문과 글자수를 붙여준다. 다른 공고의 문항으로 대신 작성하지 않는다.

## 5. 상태와 일정 확인

상태를 바꿀 때는 다음처럼 말한다.

| 환경 | 실행 예시 |
|---|---|
| Codex | `/track LG전자 지원서 작성 중으로 변경` |
| Claude Code | `/track LG전자 지원서 작성 중으로 변경` |

`submitted`는 사용자가 실제 제출했다고 확인한 경우에만 기록한다. 최종본 파일이 있다는 이유로 제출 완료 처리하지 않는다.

프로젝트 루트의 `run-dashboard.cmd`를 더블클릭하면 별도 설치 없이 읽기 전용 상황판이 열린다. 상황판에서는 마감, 적합도, 공식 확인 여부, 작성·검수·제출 상태를 확인한다.

## 6. 새 버전 받기

`run-dashboard.cmd`는 실행할 때 하루에 한 번 새 버전을 확인한다. 즉시 확인하려면 `update-chwi-ppo.cmd`를 더블클릭한다. Node.js는 필요하지 않으며 Windows 기본 PowerShell을 사용한다.

업데이트 대상은 공용 스킬·에이전트·검증 코드·대시보드다. 다음 사용자 자료는 교체하지 않는다.

- `profile/PROFILE.md`와 실제 경험 Markdown
- 실제 회사 폴더와 지원서
- `data/opportunities.json`
- 작성·검수·제출 상태

Git으로 받은 폴더는 추적 파일에 로컬 변경이 없을 때 `git pull --ff-only`로 갱신한다. 로컬 변경이 있으면 덮어쓰지 않고 업데이트를 중단한다.

`Download ZIP`으로 받은 폴더는 처음에 `release-manifest.json`이 없어도 정상이다. 첫 업데이트부터 내려받은 릴리스와 각 파일의 SHA-256을 확인하고 기존 공용 파일을 `.updates/backups/`에 백업한 뒤 교체하며, 이후 검증에 사용할 manifest를 기록한다. 실패하면 백업으로 복구한다. 인터넷 연결이 없거나 업데이트 확인에 실패해도 기존 상황판은 계속 열린다.

자동 업데이트 실행기는 `v1.0.0`부터 포함돼 있다. 이후 버전은 위 방식으로 갱신된다.

## 개인정보와 GitHub

다음은 `.gitignore`에 포함되므로 GitHub에 올리지 않는다.

- 원본 이력서·성적표
- 실제 개인 프로필과 경험 파일
- 회사별 JD·초안·최종 지원서
- 실제 공고·진행 상태와 생성 상황판

공개 저장소에 push하기 전에는 다음을 실행한다.

```powershell
npm run privacy-check
git status
```

`git status`에 개인 파일이 보이면 커밋하지 말고 `.gitignore`와 대상 경로부터 확인한다.
