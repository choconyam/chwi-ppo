# 에이전트 실행 구조

`intake → discover → apply`가 주 흐름이며 `track`은 후순위 일정 관리다. 각 이름은 책임을 나타내며 매번 별도의 에이전트를 실행하라는 의미가 아니다.

| 단계 | 메인/코드가 먼저 할 일 | 위임이 필요한 경우 |
|---|---|---|
| intake | source 변경 계획, 작은 추출·정정, 해당 경험만 갱신 | 서로 독립적인 큰 문서/프로젝트 묶음은 Luna Max, 기본 동시 2개 |
| discover | 포털 목록 수집, 중복·확실한 불일치 검사, 미처리 큐 | 많은 목록은 job-finder, 공식 확인+JD 분석은 Luna Max 묶음 |
| 적합성 | 소수 후보 비교, 명백한 자격 불충족 조기 종료 | 큰 후보 묶음만 role-fit-checker Sol High |
| apply | compact packet·기존 매핑 재사용·검수 전 초안 작성/checkpoint | 큰 매핑·문항 묶음만 위임 |
| 선택적 사실 검수 | 사용자가 중간 검수를 요청했을 때 현재 입력·본문 해시 확보 | 작성자와 별개 Sol High가 요청 문항 검수 |
| 최종 검수 | 최종 요청 때 공고·문항 최신 여부 확인 | 새 문맥 Sol XHigh, 전체 최종본과 인용 근거 |
| track | 검증된 데이터 병합·동기화 | 모델은 사용자 상태 표현 해석에만 사용 |

## 전달할 입력

전체 대화 대신 역할, 입력 경로, 출력 경로, 필요한 판단과 중단 조건만 전달한다. 회사 원문 검증·JD 구조화 작업에는 개인 프로필을 주지 않는다. 작성·검수는 compact packet과 배정 claim을 우선하고 원자료는 실제 불일치가 있을 때 해당 위치만 추가 조회한다.

기본 초안과 사용자의 일반 수정은 fact-reviewer·revision-editor·자동 재검수 없이 요청 부분만 처리한다. 작은 정정은 0개의 서브에이전트로 처리할 수 있다. 실제 위임 필요성은 문서량과 독립성에 따라 판단한다. 검수 역할을 실행할 때는 작성자/검수자 분리를 유지한다.

## 재사용 기준

- intake: 내용 SHA와 처리 receipt. 계획을 만들었다고 자료를 읽은 것으로 기록하지 않는다.
- discover: 수집 snapshot과 후보 큐를 재사용한다. 공식 확인은 내용 지문·조건·확인 시각 기준이며, 기본 24시간 또는 마감/변경 징후에서 갱신한다.
- apply: 공식 JD·문항·배정 claim이 같고 형식 검사된 현재 파일이 남아 있으면 검수 전 초안을 재사용한다. 이 체크포인트는 PASS가 아니다. 입력이 바뀌면 기존 파일은 수정 참고본으로만 남긴다.
- optional fact review: 중간 fact PASS는 final PASS로 승격하지 않는다.
- final: 현재 입력·본문·보고서 hash의 PASS를 재사용한다. 새 final은 제출 전 전체 검수 의도가 분명할 때만 실행한다.

## 오류 처리

미확인 개인 사실은 그 claim에만, 공식 확인 실패는 그 직무에만 보류를 적용한다. 기본 초안에는 자동 검수·수정 반복을 두지 않는다. final은 제출에 영향 있는 확인 가능한 결함만 판정하고, 지적 수정 뒤 해당 지적과 변경 영향만 한 번 재확인한다. 문체 취향·학술 재감사·면접 대비로 넓히거나 자동 반복하지 않는다.

실행 명령·입출력 구조·재개 절차는 [실행 계약 색인](WORKFLOW_RUNTIME.md)에서 현재 단계 문서만 선택해 읽는다.
