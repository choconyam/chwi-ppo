# 에이전트 실행 구조

`intake → discover → apply`가 주 흐름이며 `track`은 후순위 일정 관리다. 각 이름은 책임을 나타내며 매번 별도의 에이전트를 실행하라는 의미가 아니다.

| 단계 | 메인/코드가 먼저 할 일 | 위임이 필요한 경우 |
|---|---|---|
| intake | source 변경 계획, 작은 추출·정정, 해당 경험만 갱신 | 서로 독립적인 큰 문서/프로젝트 묶음은 Luna Max, 기본 동시 2개 |
| discover | 포털 목록 수집, 중복·확실한 불일치 검사, 미처리 큐 | 많은 목록은 job-finder, 공식 확인+JD 분석은 Luna Max 묶음 |
| 적합성 | 지원 조건과 검증된 후보 묶음 준비 | role-fit-checker Sol High 한 번에 여러 직무 비교 |
| apply | claim 요약·기존 매핑 재사용·글자수 검사 | 큰 매핑은 Luna Max, 작성/수정은 Sol High |
| 사실 검수 | 현재 입력·본문 해시 확보 | 작성자와 별개 Sol High가 대상 문항 전체 검수 |
| 최종 검수 | 최종 요청 때 공고·문항 최신 여부 확인 | 새 문맥 Sol XHigh, 전체 최종본과 인용 근거 |
| track | 검증된 데이터 병합·동기화 | 모델은 사용자 상태 표현 해석에만 사용 |

## 전달할 입력

전체 대화 대신 역할, 입력 경로, 출력 경로, 필요한 판단과 중단 조건만 전달한다. 회사 원문 검증·JD 구조화 작업에는 개인 프로필을 주지 않는다. 작성·검수에는 배정된 경험 정본만 제공하고 원자료는 불일치가 있을 때 추가 조회한다.

작은 정정은 0개의 서브에이전트로 처리할 수 있다. 실제 위임 필요성은 문서량과 독립성에 따라 판단한다. 여러 역할을 묶더라도 작성자/검수자 분리는 유지한다.

## 재사용 기준

- intake: 내용 SHA와 처리 receipt. 계획을 만들었다고 자료를 읽은 것으로 기록하지 않는다.
- discover: 수집 snapshot과 후보 큐를 재사용한다. 공식 확인은 내용 지문·조건·확인 시각 기준이며, 기본 24시간 또는 마감/변경 징후에서 갱신한다.
- apply: 공식 JD·문항·배정 claim·검수 본문 해시가 같을 때만 PASS를 재사용한다. 무관한 경험 추가는 해당 문항을 다시 쓰게 하지 않는다.
- final: 과거 초안이 아닌 현재 최종 문항을 독립 검수한다.

## 오류 처리

미확인 개인 사실은 그 claim에만, 공식 확인 실패는 그 직무에만 보류를 적용한다. 다른 후보까지 일괄 중단하지 않는다. 작성 재수정은 기본 2회까지만 반복하고, 해결되지 않으면 남은 근거와 질문을 명시한다. 재시도 횟수를 채웠다는 이유로 PASS를 주지 않는다.

실행 명령·입출력 구조·재개 절차는 [WORKFLOW_RUNTIME.md](WORKFLOW_RUNTIME.md)에 있다.
