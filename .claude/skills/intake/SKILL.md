# Intake

회사·JD에 맞추기 전의 사실 정본을 관리한다. 기존 사용자 확인과 claim-id를 보존한다.

## 최초 정리와 이어하기

- 사용자가 지정한 파일·폴더와 이전에 등록한 원자료 범위만 읽는다. 다른 프로젝트 폴더는 경로가 지정된 경우에만 포함한다.
- 먼저 `.work/intake/`에서 해당 자료의 기존 `run.json`을 확인한다. 미완료 실행이 있으면 `node scripts/intake-run.mjs status --run <run.json>`으로 완료 결과와 실제 실행 중인 worker를 확인하고 이어간다. 중단됐다는 이유로 새 계획·전체 추출부터 시작하지 않는다.
- 새 자료는 `node scripts/intake-plan.mjs plan --source "<원자료 경로>" --out .work/intake/<run-id>/plan.json`으로 계획하고 `intake-run.mjs start --plan <plan.json> --run <run.json>`으로 등록한다. 기본 계획은 프로젝트 README·요약만 내용 해시를 읽고 코드·데이터·긴 로그는 미선택 목록에 둔다. 필요한 상세 파일만 별도 source로 지정한다.
- 원자료가 바뀌어 새 계획이 필요할 때는 다른 run 경로에서 `start ... --previous <이전 run.json>`으로 같은 원자료·구간의 완료 결과를 재사용한다. 이전 worker의 종료를 확인하기 전에는 재시작하지 않는다.
- 세부 CLI·receipt가 필요할 때만 [intake 실행 계약](../../../docs/runtime/INTAKE.md)을 읽는다.
- 변경이 없으면 추출·통합 에이전트를 부르지 않고 기존 프로필을 사용한다.
- 기존 프로필은 있는데 manifest가 없는 `legacy-review`이면 기존 경험의 원자료 링크와 지정 자료의 요약부터 대조한다. 기존 내용을 전부 재작성하거나 읽지 않은 자료를 처리 완료로 등록하지 않는다.
- 사용자 답변 한두 개를 반영하는 경우 해당 claim과 요약만 직접 수정한다. 질문/정정은 로컬 확인 기록에 남겨 다음 실행에서 다시 묻지 않는다.

## 읽기와 통합

1. 처음에는 이력서·성적표·기존 경험 정리·프로젝트 README/결과 보고서를 우선한다. 전체 코드, Git 전체 이력, 모든 로그는 주장 확인에 필요한 위치만 추가로 읽는다. 큰 PDF는 먼저 목차/관련 페이지를 추출한다.
2. `intake-run.mjs claim`이 반환한 원자료·구간·outputPath만 처리한다. 텍스트는 최대 12,000자 단위로 나뉜다. PDF·Office·큰 파일의 `needs-scope`는 목차/시트/슬라이드를 먼저 확인하고 `split`으로 필요한 구간을 지정한다. 변환본은 원자료 대체가 아니며 표·그림·기간·수치는 필요한 원본 위치와 대조한다. MarkItDown은 필수 의존성이 아니고 현재 사용 가능한 추출기를 쓴다.
3. 소량은 메인이 처리한다. 독립적인 큰 묶음만 document-extractor/project-extractor를 Luna Max로 기본 동시 2개 위임하고 worker ID를 남긴다. 각 구간이 끝나면 즉시 `record`하여 추출 결과를 저장한다. 전체 대화나 프로젝트 전체를 넘기지 않는다. 실패한 구간만 `fail`로 보류하고 다른 자료를 계속한다. 재시도는 1회까지이며 이후에는 범위를 줄이거나 확인 필요로 남긴다. 시간 초과는 worker 종료 증거가 아니다.
4. 통합은 한 작성자가 수행한다. profile-synthesizer는 여러 결과가 실제로 합쳐질 때만 호출한다. PROFILE 인덱스와 이번 claim의 관련 경험만 읽어 기존 claim-id·사용자 확인과 대조하고, 관련 없는 경험 파일 전체를 증분 통합 때 다시 읽지 않는다. 소규모 변경은 해당 경험과 PROFILE 인덱스만 수정한다.
5. 경력 지원자는 회사·고용형태·직무·근무 기간·개인 책임·성과를 분리한다. 겹치는 근무 기간은 단순 합산하지 않고 연구·인턴을 정규 경력으로 자동 산입하지 않는다.
6. 사실은 `검증됨 | 확인 필요 | 사용 금지`로 관리한다. 추출 완료는 사실 검증이나 프로필 반영 완료가 아니다. 삭제·이동·접근실패 때문에 기존 사실을 자동 삭제하거나 기존 사용자 확인을 취소하지 않는다. 충돌한 claim만 확인 대상으로 둔다.
7. 의미 검토와 `node scripts/validate-profile.mjs`를 통과한 묶음만 `intake-run.mjs receipt`와 `intake-plan.mjs commit`으로 부분 반영할 수 있다. 미완료·미선택 자료는 처리 완료로 기록하지 않는다. 부분 반영 후 계속할 때는 새 plan과 `--previous`를 사용한다. 학력·주요 경험·지원 조건이 준비됐다면 상세 자료가 남아 있어도 discover를 진행할 수 있다.

## 완료 보고

전체 작업 구간/추출 완료/처리 중/대기/확인 필요, 미선택 상세 자료, 새로/수정한 경험과 재개 경로를 짧게 보여준다. 확인 질문은 현재 검색·작성에 영향을 주는 것부터 최대 3개를 묶고 나머지는 questions.md에 보관한다. 주기적인 전체 재분석은 하지 않고 최초 정리 후에는 새 경험·정정 사항만 갱신한다.

프로필은 사람이 읽는 Markdown 정본이다. 검색용 요약은 [지원 조건 템플릿](../../../profile/PROFILE_TEMPLATE.md)에 맞춰 신입/경력/둘 다/미정, 기업 규모·직무·지역·입사 시점을 포함한다. 지원 유형이 미정이라고 신입으로 가정하지 않는다.
