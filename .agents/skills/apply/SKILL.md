# Apply

`/apply <회사> <직무> [문항N] [final]`. 원자료 정리는 intake의 책임이고, 캘린더 등록 여부는 작성의 선행 조건이 아니다.

## 먼저 요청에 맞는 경로 선택

- 기존 문장 수정: 해당 본문·배정 claim에서 바로 수정하고 해당 문항만 checkpoint한다. 새 사실·문항·JD가 바뀌지 않았으면 catalog·매핑·prepare·공식 사이트 재확인을 반복하지 않는다. packet이 없는 기존 파일은 해당 근거와 제한을 확인해 독립 형식 검사만 한다.
- 문안 설명·평가만 요청: 답변만 하고 파일 수정이나 검수 보고서를 만들지 않는다.
- 새 초안 또는 입력 근거 변경: 아래 입력 준비를 수행한다. 현재 입력과 일치하는 기존 매핑·request·packet은 재사용한다.
- 실제 제출 전 전체 검수·제출본 확정 요청: final 절로 간다. 일반 문장 수정은 final이 아니다.

## 새 초안의 입력 준비

1. 선택한 직무의 공식 JD·분석·적합성, 실제 문항 원문·글자수를 확인한다. 로그인 뒤에만 보이는 문항은 사용자에게 그 문항만 요청한다. 비슷한 회사 문항을 대신 만들지 않는다.
2. 자격 `needs-review/ineligible`, 적합성 `재검토`이면 해결할 조건을 밝히고 해당 직무의 제출용 작성을 보류한다. 다른 직무나 검증된 경험 작업까지 중단하지 않는다.
3. `apply-packet.mjs catalog`의 검증 사실 요약으로 문항별 claim을 배정한다. 경험이 많으면 `--mode index --limit 30`으로 인덱스를 보고 `--files`로 관련 경험만 읽는다. 미검토 범위를 남기며 검색 결과 없음과 경험 부재를 구별한다. 적은 문항은 메인이 evidence-matcher 역할을 수행하고, 대규모 문항 묶음만 Luna Max에 넘긴다.
4. `03_소재매핑.md`와 `application-request.json`을 [apply 실행 계약](../../../docs/runtime/APPLY.md)의 형식으로 만든다. 문항 원문마다 질문 의도·한 문장 핵심 답·주력/보조 근거를 먼저 정하고, 새 초안의 답변 방향을 request의 `answerPlan`에 압축한다. 01이 문장별 형식이면 [JD 매칭 계약](../../../docs/runtime/JD_MATCHING.md)의 검토 기록을 재사용하고 문항 → 요구 ID → claim을 연결한다. 요구 전체를 모든 문항에 억지로 배정하지 않는다. 입력이 바뀌면 로컬 check의 영향 항목만 재판단하며 원문 전체·모든 경험을 반복 전달하지 않는다. 근거가 부족한 문항만 필요한 사용자 사실을 확인하거나 intake 갱신으로 돌린다.
5. `apply-packet.mjs prepare`의 compact `packet.md`를 우선 읽는다. 검증용 JSON은 입력 전문/hash를 유지하지만 모델용 Markdown은 JD 분석·선택 claim·공통 표현 제한을 중복 없이 제공한다. 누락이나 실제 불일치가 있을 때만 연결된 JD/경험 원문 위치를 추가 확인한다. `draft`만 새로 쓰고, `reuse-draft`는 checkpoint된 검수 전 초안, `reuse-final`은 현재 입력·본문·보고서 hash가 유효한 final PASS다.

## 작성과 검수

- 현재 메인이 소수 문항의 매핑·작성·수정을 끝낸다. Luna/Sol 역할이 있다는 이유로 이관하지 않는다. 명백히 큰 독립 작업만 matcher/writer에 맡긴다. 신입/경력 모두 실제 본인 역할·판단·결과가 드러나게 쓴다. 배정된 검증 claim에 없는 사실·수치·성과를 만들거나 준비·진행 상태를 완료로 높이지 않는다. unknown만 질문하거나 제외하고 나머지는 즉시 작성한다.
- 지원동기·입사 후 기여 문항은 공식 JD에서 확인한 해당 회사·조직의 사업 맥락과 직무 과제를 본인의 검증된 판단·행동·성과에 연결한다. 회사명만 다른 곳으로 바꿔도 성립한다면 JD 문구나 슬로건을 더 붙이지 말고 선택 이유와 기여 방식을 다시 쓴다. 경험·가치 문항에는 질문과 무관한 회사 설명을 억지로 넣지 않는다.
- 첫 초안부터 문항마다 질문에 직접 답하는 중심 주장을 한 문장으로 정하고, 사례의 구체적 판단·행동·결과가 이를 입증하게 한다. 지원동기·기여 문항은 회사·직무 선택 이유를, 역량·협업·가치관 문항은 질문이 요구한 행동과 배움을 우선한다. 수치·도구를 쓸 때는 무엇을 판단하려고 사용했고 어떤 결론으로 이어졌는지 밝힌다. 전달 전 각 문장이 새로운 사실이나 인과관계를 더하는지, 필요한 회사·직무 연결이 구체적인지 점검하고 같은 교훈의 반복·직무 나열은 덜어낸다. 여러 문항에 같은 경험을 쓰더라도 문항별로 증명하는 면을 나눠 같은 설명을 반복하지 않는다.
- 강점은 본인이 맡은 판단과 확인된 결과로 분명히 보여준다. 겸손은 공동 기여·검증 범위를 정확히 밝히고 협업 상대의 관점을 존중하는 방식으로 드러낸다. 약점을 선제적으로 나열하거나 자기 성과를 깎아내리지 않되, 성과를 오해하게 만드는 사실 생략도 하지 않는다.
- `04_초안/`에 문항별 하나의 text 블록과 claim 추적표를 둔다. packet이 있으면 `apply-packet.mjs checkpoint` 한 번으로 형식·placeholder·글자수·claim 추적을 검사한다. `check-submission.mjs`는 packet에 속하지 않는 독립 파일만 검사한다. 글자수 상한을 첫 초안부터 충분히 활용한다. 사용자가 상한과의 차이 등 분량 목표를 정했다면 실제 본문 글자수를 재서 그 범위에 맞추고, 목표가 없더라도 상한의 10% 이상을 남겼다면 구체적 근거·판단·문항에 필요한 회사·직무 연결을 더 담을 수 있는지 다시 살핀다. 반복·일반론·미확인 사실로 채우지 못해 목표에 못 미치면 부족한 이유와 현재 글자수를 알린다. 형식 검사는 회사별 설득력을 판정하지 못하므로 메인이 문항 의도와 회사명 교체 가능성을 직접 점검한다.
- 저장과 해당 문항의 형식 검사가 끝나면 `검수 전 초안`이라고 분명히 알려 바로 전달한다. 형식 오류는 해당 부분을 고치고 같은 검사를 재실행하되 새 실패나 변경이 없으면 반복하지 않는다. 기본 작성에서는 fact-reviewer, revision-editor, 자동 재검수 루프를 호출하지 않는다. 초안 체크포인트는 PASS·`ready`·최종본이 아니다.
- “최종 문장 좀 바꿔”를 포함한 일반 수정은 요청한 문항·부분만 직접 바꾸고 checkpoint만 갱신한다. 표현에 `최종`이 들어갔다는 이유로 final을 호출하지 않는다. 새 사실이 필요한 부분만 질문하거나 제외하며 다른 문항을 다시 쓰지 않는다.
- 사용자가 중간 사실 검수를 명시적으로 요청한 경우에만 작성자와 별개인 fact-reviewer(Sol High)를 호출한다. `record --stage fact` 기록은 선택 검수 이력일 뿐 최종 PASS가 아니다.
- humanizer-ko는 사용자가 명시적으로 요청했을 때만 최종 검수 전에 적용한다. 문체가 바뀐 문항만 checkpoint한다.

## final

내용 확정 뒤 실제 제출 전 전체 검수·제출본 확정을 요청했을 때만 실행한다. 공식 공고·자격·문항의 변경 여부를 확인하고, 변하지 않은 분석·매핑과 현재 입력·본문·보고서 hash의 final PASS는 재사용한다.

새 검수는 작성 문맥을 넘기지 않은 final-red-team-reviewer(Sol XHigh) 하나가 전체 문항을 한 번 확인한다. 검수 대상은 제출에 영향 있는 사실·수치·기간·역할·상태 불일치, 문항/자격 미충족과 문항 간 모순뿐이다. 문체 취향·가상 우려·학술 재감사·면접 대비는 제외한다. compact packet과 인용 claim을 우선하고 실제 불일치 때만 해당 원문을 읽는다.

REVISE는 지적된 부분만 수정한 뒤 수정 영향까지 한 번 재확인하고 자동 반복하지 않는다. 미해결 결함은 보고한다. final PASS 기록과 민감정보 검사를 통과한 현재 파일만 `최종/`에 복사한다. 보고서 해시·record 명령이 필요할 때만 [apply 실행 계약](../../../docs/runtime/APPLY.md)의 final 절을 확인한다. `submitted`는 사용자가 실제 제출을 확인해야 기록한다.
