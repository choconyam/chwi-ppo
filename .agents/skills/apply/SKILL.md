# Apply

`/apply <회사> <직무> [문항N] [final]`. 원자료 정리는 intake의 책임이고, 캘린더 등록 여부는 작성의 선행 조건이 아니다.

## 입력 준비

1. 선택한 직무의 공식 JD·분석·적합성, 실제 문항 원문·글자수를 확인한다. 로그인 뒤에만 보이는 문항은 사용자에게 그 문항만 요청한다. 비슷한 회사 문항을 대신 만들지 않는다.
2. 자격 `needs-review/ineligible`, 적합성 `재검토`이면 해결할 조건을 밝히고 해당 직무의 제출용 작성을 보류한다. 다른 직무나 검증된 경험 작업까지 중단하지 않는다.
3. `apply-packet.mjs catalog`의 검증 사실 요약으로 문항별 claim을 배정한다. 적은 문항은 메인이 evidence-matcher 역할을 수행하고, 대규모 문항 묶음만 Luna Max에 넘긴다.
4. `03_소재매핑.md`와 `application-request.json`을 [실행 계약](../../../docs/WORKFLOW_RUNTIME.md)의 apply 형식으로 만든다. 근거가 부족한 문항만 필요한 사용자 사실을 확인하거나 intake 갱신으로 돌린다.
5. `apply-packet.mjs prepare`로 배정된 claim·역할 제한·문항·JD만 포함한 입력 묶음을 만든다. 같은 근거·문항·본문에 대한 PASS가 있으면 재사용한다. 바뀐 입력을 이전 PASS로 처리하지 않는다.

## 작성과 검수

- 메인이 Sol High 작성 역할을 수행하거나 draft-writer 한 번에 대상 문항을 묶어 맡긴다. 신입/경력 모두 실제 본인 역할·판단·결과가 드러나게 쓴다. 경력자는 담당 업무·프로젝트 책임·이직 목적 등 해당 문항이 요구하는 내용을 쓴다.
- `04_초안/`에 문항별 하나의 text 블록과 claim 추적표를 두고 `check-submission.mjs <파일> <제한>`으로 검사한다.
- 작성자와 별개인 fact-reviewer(Sol High)를 한 번 호출해 대상 문항을 함께 검수한다. 모든 원자료 대신 공식 문항과 사용한 경험 정본만 전달하고 불일치가 있는 근거만 원천 자료로 확인한다.
- 보고서에는 판정, 입력 해시, 실제 검수 본문 해시를 남긴다. `apply-packet.mjs record`는 현재 입력·본문에 맞는 PASS만 재사용하도록 기록한다.
- PASS면 검수한 파일을 `06_수정본/`에 그대로 보관한다. REVISE면 revision-editor가 지적 문항만 수정하고 해당 문항을 재검수한다. 기본 최대 2회 재수정 후에도 같은 문제면 미해결 지점과 필요한 사실을 보고한다. 반복 제한 도달은 PASS가 아니다.
- 의미·수치·역할에 영향 없는 형식 변경은 결정론적 검사로 확인한다. 새 claim이나 사실 변경은 다시 사실 검수를 받는다.

## final

사용자가 최종본을 요청하면 공식 공고 상태/자격·문항 변경 여부를 확인한다. 변경 없으면 기존 분석·매핑은 재사용한다. final-red-team-reviewer(Sol XHigh)는 작성 대화·이전 판정 없이 독립적으로 전체 최종 문항과 해당 근거를 읽는다.

수정이 있으면 변경 문항과 문항 간 일관성을 재검수하고, 모든 최종 파일이 현재 PASS 범위에 속할 때만 민감정보 검사 후 `최종/`에 복사한다. `submitted`는 사용자가 실제 제출을 확인할 때만 기록한다. humanizer-ko는 요청할 때만 실행한다.
